# Maintaining the three-stage collection

[Contribution guide](../CONTRIBUTING.md) · [Collection](../README.md)

`data/works.yaml` and `data/site.yaml` are the canonical public sources. `scripts/build_readme.py` generates the English, Chinese, and Japanese root READMEs. Do not edit generated entries directly. The public layout identifier is `three-stages-v1`: 19 numbered sections across three stages, plus the Survey entry `SV`.

## Entry contract

| Field | Meaning |
|---|---|
| `id` | Stable, unique identity; arXiv IDs omit version suffixes. Official reports may use a non-arXiv ID. |
| `aliases` | Explicit alternative identities, such as a later arXiv ID for an existing report. Never create a second entry for the same work. |
| `title`, `date`, `url` | Official title, first-publication month (`YYYY.MM`, when known), and primary source. |
| `sources` | All retained original paper, project, code, dataset, and demo URLs, including `url`. |
| `type` | `paper`, `resource`, `demo`, or `reading`; count papers by this field, not by section. |
| `scope` | `core`, `adjacent`, `resource`, `survey`, `demo`, or `reading`. A Survey is a paper with Survey scope; a resource or application does not become a paper because it has Adjacent scope. |
| `section`, `sub` | One canonical location. Use the section's allowed subgroups from `site.yaml`; this position is independent of scope. |
| `tldr.en`, `tldr.zh`, `tldr.ja` | Concise, equivalent summaries with the same limitations and attribution. No empty translations or placeholders. |
| `verification` | Retained English and Chinese evidence for Core entries: construction, execution, multimodal observation, subsequent revision, and what is checked. |
| `see_also` | Other relevant section IDs linking back to this record. Add only for a supported contribution. |
| `setup` | Optional experimental setup, mainly for Stage 3: `engines` (simulators or engines the work runs in), `sim_robots` (robots used in simulation) and `real_robots` (hardware). Each is a list of proper names, so no translation is needed; omit an empty list. Rendered under the summary as one line, simulation first, then hardware. |

For `setup`, list the engines used in the reported experiments. Use official code to verify the reported setup and describe alternative public implementations separately. Name the underlying engine for each benchmark: LIBERO, robosuite and RoboCasa are `MuJoCo`; ManiSkill, RoboTwin and SimplerEnv are `SAPIEN`; RoboDojo and BEHAVIOR/OmniGibson are `Isaac Sim`; RoboLab is `Isaac Lab`; CALVIN is `PyBullet`; RLBench is `CoppeliaSim`. Stand-alone simulators keep their own name (Habitat, AI2-THOR, AirSim). Use the robot model the paper states, such as `Franka Panda`, `Franka FR3`, `ARX X5` or `AgileX PiPER`; when a paper gives only a make, write the make (`Franka`), and leave out a robot the paper does not name.

A section in `site.yaml` may carry an optional `guide` (one Markdown block per language) rendered under its heading; section 3.3 uses it for a fidelity-level overview table that links to `stage3/simulator-evaluation.md`, and section 3.4 for a data overview table. The 3.4 table is written in HTML rather than Markdown so that its first column can merge with `rowspan`; keep it free of blank lines, link works with `<a>` tags pointing at their `paper-…` anchors, and mark type cells `nowrap` so they do not break mid-word. Each layer is its own `<tbody>`. Its first column is the outer layer: whether the data comes from the real world (`Real`), from simulation (`Sim`), or from both (`Real+Sim`), in that order. The section's subgroups `real-data`, `sim-data` and `mixed-data` use the same three names and order, so an entry's subgroup must match its row. Within a layer, rows give the type (demonstrations, meaning frames plus robot actions; human video; an environment replicated from real video; failure labels), the frame modality (such as multi-view RGB, RGB-D or point clouds), and where the trajectory comes from. Works whose modality differs get their own row, and identical adjacent type cells merge. Each 3.4 entry summary states the same facts in full: frames, trajectory, labels and scale. Keep the guides' work links in sync when entries move, and place a new 3.4 entry in one of its rows. The 3.3 table has one row per check in that guide: the P0 gate, then L0a, L0b, L1, L2a, L2b, L3a, L3b-1, L3b-2, L4a and L4b. A row with no work yet says so instead of staying empty, and a work that covers two rows is listed in both. That guide, `stage3/simulator-evaluation.md` and its Chinese translation, opens with an overview figure. The figure's data is `eval_ladder` in `site.yaml`. It holds an English and a Chinese title, lead, note and words inside the pictures, plus five stages of eight cards. A card is a level or one of its dimensions: L2 and L4 are one card each, L3b is split into L3b-1 and L3b-2, and the P0 gate is not drawn. Each card has a code, pictogram, name, question and the fake simulation it exposes, and lists its works as `<work id>` or `<work id> †` for an evaluator; the figure shows only their count. `scripts/eval_ladder.py` renders a light and a dark SVG per language into `assets/eval-ladder/`, and `--check` fails on an unknown work id, a missing translation or a stale image. When a work moves between levels, update the guide's tables and these lists together.

Section 3.2 uses its `guide` for an input table and a representative build-stage chart, placed with the `{stage_chart}` placeholder. `scripts/stage_chart.py` draws the chart from `stage_chart` in `site.yaml`: localized legend, groups, columns and tags, then one row per work with nine cells, each `n` or `[kind, who, what]` (kind `a` Agent or VLM, `t` specialised tool, `g` given, `x` no physics engine, `r` sim-ready). It also draws the full chart at the top of `stage3/simulator-construction.md` and its Chinese translation from `stage_chart_full`: one row per 3.2 work with an 11-letter `steps` string (the nine steps, then verification & revision and variant expansion) and a physics-engine `tier` (`F` full simulator, `R` sim-ready, `S` scene only, `U` not stated) that must agree with step ⑦. When a work joins or leaves 3.2, add or remove its row there. Both charts are written to `assets/stage-chart/` and checked by `--check` like the README.

A section may list some of its subgroups in `contents_subs`. Each one gets a stable anchor, `s<section>-<subgroup>` (for example `s3-6-experiments`), and is listed in the contents, indented under its section, with its own entry count. A section may also carry `sub_see_also`, mapping a subgroup to IDs of works whose primary entry is in another section. They are rendered as a "See also" line at the end of that subgroup. Section 3.6 uses both for its Scientific experiments (AI4Science) subgroup. In `stage3/README.md` and its Chinese translation, keep that subgroup's line of links to other sections in sync with `sub_see_also`.

A stage may also carry `extras`: unnumbered reference blocks, each with an `anchor` and a localized `title` and `body`. They are rendered after the stage's numbered sections and listed in the contents without a count. They hold no entries and do not change the 19 numbered sections. Stage 3 uses one (`s3-engines`) for the simulation-tool coverage map. Its body places the map with the `{engine_map}` placeholder. The map's data is `engine_map` in `site.yaml`: localized legend, groups, columns, cell labels and alt text, plus one row per tool with eight cells written as `<level>[*<span>] [<label>]` (levels `core`, `basic`, `none`, `inherit`). `scripts/engine_map.py` renders a light and a dark SVG per language into `assets/engine-map/`; the generator writes them with the READMEs, and `--check` fails when one is stale. Base each cell on the tool's official documentation; coverage levels are a broad judgment, not a score. Below it, `{engine_strengths}` places a strengths heatmap from `engine_strengths`: eight localized dimensions, grouped by `groups` into the coverage map's A–D blocks in pipeline order, and one row per tool with eight scores from 1 to 3 (for example `"3 1 2 1 2 1 1 3*"`), where `*` marks the single top pick in each column. It is rendered to `assets/engine-map/engine-strengths-*.svg` and checked the same way.

The generator names supporting links by destination type using the localized `source_labels` in `data/site.yaml`. Record URL exceptions in `source_kind_overrides` when the destination cannot be inferred from its address. Stage 3 reading entries use the same labels. Keep all source URLs in the catalog. The generated entry displays one entrance per paper, using the linked title first. Record verified copies across publishers in `paper_url_aliases` and name direct section links in `source_kind_overrides`.

For new and revised entries, follow resource links from the official project page, paper, or repository. Add direct links to public code, datasets, demos, and model releases. Check that code links lead to implementation files and label repositories that contain only documentation or compiled releases by their actual contents.

Stage 1 covers visual feedback in artifact construction; Stage 2 covers models used as tools; Stage 3 covers the digital–physical loop. Method, evaluation, data, training, and resource roles remain distinct within these perspectives. A dataset release, a data-construction method, and experimental data are different contributions.

Scope identities stay in canonical data and metadata comments for maintenance. Public entries display the title, source links, and summary without scope badges. Every generated entry has a `mmac-record` comment with `id`, `scope`, `primary`, `stage`, and `type`, and a stable `paper-…` anchor. `site.yaml` also retains older anchors through `anchor_aliases`. Update local references to current anchors while keeping published aliases working. Preserve source URLs when reorganizing entries; a primary link alone is insufficient if earlier entries included supporting code or data.

## Interactive walkthroughs

A section may list walkthrough pages under `guides`. Each walkthrough is an interactive web page kept in this repository and served by GitHub Pages: `page` is its file in the repository, `url` is the address that serves it, and `title` and `note` are localized. Both `page` and `url` accept either one shared string or an `en`/`zh`/`ja` mapping with every language present. The generator puts a 📖 link to the matching language's URL at the top of the section. Set `in_contents: false` on a walkthrough to omit its link from the contents.

Section 3.4 links to `stage3/droid-data/`, which takes two real DROID episodes apart. The Chinese (`index.html`), English (`index.en.html`) and Japanese (`index.ja.html`) pages contain their translated prose and share `styles.css`, `app.js`, the dynamic translations in `i18n.js`, the episode data (`cases.json`) and the camera frames (`media/`). Keep all prose, accessibility labels, metadata explanations, phase names, key-frame labels and error messages translated; language links preserve the selected case. GitHub Pages serves the repository from the `main` branch root (Settings → Pages → Deploy from a branch → `main` / root); the empty `.nojekyll` file makes Pages serve the files as they are. `--check` fails when a language's page file is missing, when its URL does not end with that page's path, or when its title or note is missing. Check both cases in all three languages at desktop and mobile widths after changing the shared viewer.

## Robotics branch repository

[awesome-multimodal-agentic-coding-robotics](https://github.com/jiangjin1999/awesome-multimodal-agentic-coding-robotics) publishes one stage of this map as its own list, presented as a git branch of this repository. Two rules hold. First, Stage 3 and the cherry-picked 2.6 are identical in both repositories, because both are generated from `data/works.yaml`. Second, every update to those works reaches both: the build regenerates `robotics/` and `assets/robotics/`, they are committed with the data, and the robotics repository copies them from `main`.

The `robotics` block in `data/site.yaml` defines the branch: `repo`, the output folder `dir` (`robotics/`), the checked-out `stage` (3), the `cherry_pick` sections taken from other stages (`2.6`), the `title`, the `console` lines shown under the header, localized `text`, and the `taxonomy`. `main_note` is the line under the Stage 3 intro in the root READMEs that points to the branch; the root READMEs also carry a `branch · robotics` badge.

The branch README opens with its own hero image, an overview, and a Taxonomy section holding the taxonomy figure and table, then explains where the branch comes from with a Mermaid `gitGraph`. The hero is `robotics.hero` (light and dark PNG paths and an English alt text). Like the root hero, it is drawn by a script run by hand: `NODE_PATH=$(npm root -g) node assets/robotics/hero/gen.js` writes `assets/robotics/hero/hero-{light,dark}.{svg,png}`. It holds no counts or section names, so it does not go stale. Without `robotics.hero`, the taxonomy figure takes the top slot. `taxonomy.steps` lists the steps of one Real2Sim2Real loop in order: Act (3.1, 2.6), Build (3.2, 3.3), Learn (3.4, 3.5) and Apply (3.6). Each step has a `world` (`real` or `sim`), a localized `label` and `title`, and its `sections`; every branch section must be in exactly one step, or `--check` fails. `scripts/robotics_map.py` draws the figure from these steps and the entry counts into `assets/robotics/`, a light and a dark SVG per language, with an alt text built from the same steps. The taxonomy table replaces the contents: one row per step, linking each section and, when a section has several, its subgroups. Every subgroup gets an anchor, `s<section>-<subgroup>`. Keep commit labels on the git graph's main line short, because long rotated labels overlap the branch name. When a section is added to or removed from Stage 3, place it in a step.

`scripts/build_readme.py` writes the branch's three READMEs, `CONTRIBUTING.md`, `AGENTS.md`, `CLAUDE.md` and a copy of `LICENSE` into `robotics/`, and `--check` fails when they are stale. They reuse the root rendering: the same entries, section numbers, `paper-…` anchors and section guides, without the retired `anchor_aliases`. A link with no target in the branch README is rewritten to this repository: fragments to the same-language root README, images to `raw.githubusercontent.com`, and other files to their `blob/main` page. Only the branch READMEs and `LICENSE` stay local.

The branch repository maintains only `.github/workflows/sync.yml`. Every hour, or when run by hand, it copies `robotics/` from `main` here, replaces the footer link `upstream@main` with the last upstream commit that changed `robotics/`, and commits `Sync from upstream @ <commit>` when anything differs. Changes therefore reach the branch only after they are merged to `main`. Never edit the branch repository's generated files directly: the next sync overwrites them.

## Validation and publication

Run the commands in the [contribution guide](../CONTRIBUTING.md#submit-a-pull-request). `--check` requires all translations, exact generated output, valid identities and scopes, and existing local files and fragments across the documentation. The GitHub Actions workflow runs the public checks on pull requests and pushes to main. The regression suite covers missing translations, lost evidence, source/ID mismatches, duplicate identities, and old cross-file links. It does not replace reading the primary sources or checking the claims in a summary.

Before publishing, compare the canonical ID/scope/source inventory with the previous main, inspect the rendered READMEs at mobile and desktop widths, and review the diff. Preserve release announcements, version information, and CITATION unless a maintainer explicitly requests a release change. Update the maintenance date only for real content changes.

Automated update runs follow the [automated update rules](./AUTO_UPDATE.md) and record every candidate decision in `data/triage.yaml`, which `--check` validates against the catalog. The research workspace has additional private discovery, preservation, and digest checks. Its 12 discovery directions and method/evaluation/data searches are search axes, not public section numbers. New daily records use `routing.primary`, `routing.stage`, optional `routing.discovery_directions`, and evidence-bearing `routing.related` references with a saved `three-stages-v1` repository map. Historical `directions-v4` digests keep their original maps and rendering; a layout migration does not authorize resending a delivered email.
