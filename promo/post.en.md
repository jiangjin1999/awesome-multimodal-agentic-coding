## Full text

### A Multimodal View of Coding | Awesome Multimodal Agentic Coding

**Pushing the limits of agents, toward physical AGI**

We’ve been talking with some friends lately, and they found our angle rather interesting, so here are our thoughts.

We started working on multimodal agentic coding in June. After GPT-6 came out, computer-use agents suddenly took off, and some of the research we had been doing right at the edge of model capabilities started to feel less cutting-edge (working on it alone was also pretty slow).

But we have always looked at this from a coding angle rather than a CUA angle. Robot-use agents are becoming more common too: agents write code to control robots directly, and together with Real2Sim2Real, these are all extensions of multimodal coding into the physical world. In fact, from a coding angle, this progression is quite natural.

We understand it in three stages:

1️⃣ Visual as Feedback: with visual feedback, the model can truly run in a loop

2️⃣ Agent Orchestrates Models: let the agent call generation, perception and action models, pushing its limits further

3️⃣ Bridging Digital & Physical: build simulators and control robots with code, from the screen to the real world

#### 1 - Visual as Feedback: With visual feedback, the model can loop

Better visual feedback and perception let the model truly run in a loop.

Compared with an ordinary coding agent, the key to a multimodal coding agent is visual feedback, and that greatly expands what the agent can do. Web pages, charts, slides, 3D/CAD, games… anything that runs and can be seen can go into this loop.

Atomic multimodal abilities such as perception, grounding and diff are the foundation: seeing accurately, finding the right spot, telling what changed. Only with precise feedback can the coding loop run well.

Of course, various workflows could already bring in visual feedback; but in the agent setting, the model is no longer just doing VQA: it can compare on its own and optimize the whole “multimodal repo”.

#### 2 - Agent Orchestrates Models: Let the agent call other models

The agent orchestrates all kinds of models (other VLMs, generative models, action models and so on), which further expands what it can do and makes it more efficient.

Visual feedback gives the agent a huge multimodal task space. But if the agent can only look and act by itself, it not only suffers from hallucinations caused by long context, it may also need a huge amount of compute; calling other models as tools effectively improves both efficiency and quality.

Orchestration shows up on both the input and the output side:

- **Input**: use models that are better at the job to give the agent observations from different dimensions, such as detection, segmentation, depth and reconstruction;
- **Output**: call generative models for mask inpainting or for a composition based on a grey-box model; or call an action model to control a robot arm.

The first two stages lay a solid foundation for the third: visual feedback lets the agent see the result of every step, and calling models as tools lets it borrow the abilities of perception, generation and action models. Stepping into the physical world relies on exactly these two.

#### 3 - Bridging Digital World & Physical World: Bring the loop into the physical world

The first two stages keep expanding what coding agents can do, but they still live in the digital world. Naturally, we want to bring this loop into the physical world. This is also the largest and fastest-growing part of our repo.

The agentic loop is where every idea starts. Now the code controls a robot, and “look at the result, fix the code” becomes “look at what the robot did, fix the policy”. That is exactly what recent robot-use agents do: without training a dedicated policy, you give an off-the-shelf coding agent a terminal and the robot’s perception and motion interfaces, and it writes Python to get the robot working, watches the camera and the execution results, and rewrites the code when something fails. But a loop on a real robot is slow and expensive, so the natural next step is to “move” the real world into code first, and the progress of the first two stages makes Real2Sim possible; the loop can then spin fast and often in simulation, generating data and building up experience, before the skills are carried back to the real robot. And all of this, once again, comes down to the foundation model.

#### Finally

The three stages build on each other. We believe that by following the path of “write code → see the result → fix it”, agents will move step by step from the screen into the physical world.
