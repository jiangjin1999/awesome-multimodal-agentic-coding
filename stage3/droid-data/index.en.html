DROID data explained · Two real recordings

Reading one DROID episode

DROID is a public robot dataset. People at several labs use VR controllers to teleoperate the same type of robot arm, a Franka, through everyday tabletop tasks. Each attempt becomes one recording, or episode. Here we unpack two real episodes to see what they contain and what the trajectory numbers mean.

One episode, one folder

The folder name identifies the episode: lab_robot-ID_date_time. It holds three kinds of information: the trajectory (numbers), video (images), and metadata (information about the recording).

What the metadata tells us

How the three fit together

Video shows what happened visually; the trajectory records exactly how the arm moved. Timestamps align each step with a video frame. Metadata tells us which lab recorded it, what the task was, and whether it succeeded. The trajectory and video are the main ingredients used to teach a robot.

The full dataset also includes a wrist-camera recording, from a camera mounted above the gripper. This page does not use it.

The trajectory: one row per step

The robot records roughly 14 times a second; each record is a step. Each step captures the state of the arm’s “hand,” or gripper. The seven main values are:

Position (m)
Orientation (rad)
Gripper

Position: x, y, z. Measured in meters from the robot base. x is forward, y is left (negative means right), and z is height above the base. In the top view, the base is at the bottom, x points up, and y points left.

Orientation: roll, pitch, yaw. These describe rotation in radians (3.14 is about 180°). Think of your own hand: roll is like turning a doorknob, pitch tilts the hand up or down, and yaw turns it left or right. The DROID gripper mostly points downward, so roll stays near ±3.14.

Gripper: 0 means fully open; 1 means fully closed.

All 67 fields in trajectory.h5

HDF5 packs many arrays into one file, arranged in a folder-like hierarchy. Each field has one row per step, so its first dimension is the step count (97 in case A). The groups below organize them by use; the group in blue is the most commonly used.

observation/robot_state/…10 fieldsThe robot’s measured state. The three main fields are end-effector pose, cartesian_position (6 values per step: x, y, z, roll, pitch, yaw); gripper opening, gripper_position (1 value per step); and the seven joint angles, joint_positions. The rest record joint velocities and torques.
action/…8 fieldsThe command issued at this step, stored in several forms: end-effector pose and velocity, joint angles and velocities, gripper opening, and target values prefixed with target_.
action/robot_state/…10 fieldsRobot state read after executing this step’s command. It is almost the same as the next step’s measured state (less than 2 mm apart in these recordings) and is usually not needed here.
observation/camera_extrinsics/…10 fieldsEach camera’s position and orientation in the base coordinate frame (again, 6 values). External cameras stay fixed, so their values do not change between steps; the wrist camera moves with the hand. left/right identify the two views of each stereo camera.
observation/timestamp/…22 fieldsTimes of the events within each step, in milliseconds or nanoseconds, used to align video frames with trajectory rows. skip_action marks steps whose actions should be excluded.
observation/controller_info/…4 fieldsController state: whether it is on, whether motion is enabled, and whether the operator pressed success or failure.
observation/camera_type/…3 fieldsCamera type: 0 is the wrist camera; 1 is an external camera.

Things to watch when using this data

  1. Coordinates are relative to the robot base. x is forward, y left, z up; positions are in meters and angles in radians. Transform them before using a robot placed differently.
  2. Roll jumps between ±3.14. With the gripper pointing down, roll is near 180°. Although 179° and −179° are only 2° apart, their radian values differ by about 6.28. Case A crosses this boundary four times: for example, +3.14 at step 19 becomes −3.12 at step 20. Directly averaging or interpolating these numbers gives the wrong result; first convert to another representation, such as quaternions.
  3. Exclude steps marked skip_action. The operator has not enabled motion, or has already released it. The hand stays still and the recorded commands should not be used.
  4. Your tools may use the opposite gripper convention. DROID uses 0 = open and 1 = closed; uni-robot-agent uses 0 = closed and 1 = open. Invert the values before feeding DROID data to that harness.
  5. The timing is not perfectly uniform. The nominal rate is 15 steps per second, but these recordings have 66–76 ms between steps, averaging about 14 steps per second. Video also has one frame per step: align by timestamps instead of assuming perfectly regular intervals.
  6. Keep commanded and measured values distinct. Use measured values to find where the hand actually went; use commands to imitate where the operator wanted it to go. Positions differ by roughly 3 cm on average, and the gripper values differ more.
